# 0006 - Canonical Event Model

## Status
Accepted

## Context
Telemetry is generated by different components (agents, OT sensors) and processed by various central systems (ingestion, detection, correlation, storage). Disparate formats complicate correlation and increase parsing overhead.

## Decision
RedCyberFox components use one canonical security-event model across endpoint, OT sensor, ingestion, correlation, storage, and dashboard layers.

The canonical envelope preserves these fields:
- event_id
- tenant_id
- site_id
- asset_id
- sensor_id
- occurred_at
- received_at
- seq_no
- source
- category
- severity
- confidence
- protocol
- src
- dst
- action
- metadata
- rule_id
- rule_version
- attck_enterprise
- attck_ics
- quality_flags
- schema_version

## Rationale
A single, strictly enforced schema enables universal correlation, simplified storage partitioning, and predictable dashboard analytics without requiring constant data transformation at every boundary.

## Alternatives considered
- **Independent schemas per component**: Rejected because it pushes the normalization burden onto the correlation engine and analysts, increasing complexity.
- **Elastic Common Schema (ECS)**: Considered, but a purpose-built OT-native canonical model is lighter and more directly aligned with the required asset and ICS ATT&CK attributes.

## Consequences
- Every new telemetry source must map its output to this schema before ingestion.
- Strict schema versioning and backward compatibility policies must be maintained.

## Architectural invariants
- Canonical event schema is mandatory.
- Components should not invent independent event formats for core telemetry.
